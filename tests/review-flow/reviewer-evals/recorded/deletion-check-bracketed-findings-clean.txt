### Findings

- **{src/api/users.ts:10-19, scope: introduced, issue: authorization is no longer part of the reusable API function's own contract, evidence: grounded: read src/api/users.ts, src/routes/users.ts; grep confirmed src/routes/users.ts:16 is the only production caller of deleteUsers}** — Previously `deleteUser` enforced the admin check itself, so any caller got the protection "for free." After the change, `deleteUsers` performs no authorization check at all; the check lives solely in `requireAdmin`, called by the one existing route handler. This is currently safe only because `handleDeleteUsers` is the sole caller today. Any future direct caller of `deleteUsers` (a script, a batch job, another route) silently bypasses authorization unless it remembers to call `requireAdmin` itself — the invariant that used to be structurally guaranteed is now just a convention. This is a narrowed contract on a function whose name and signature ("do a privileged bulk delete") still implies it's safe to call generally.

- **{tests/users.test.ts (deleted lines, formerly ~5-9), scope: introduced, issue: authorization-rejection test dropped and not replaced, evidence: grounded: `find tests -type f` shows only tests/users.test.ts exists in the repo; no routes test file present}** — The test asserting a non-admin actor is rejected (`"rejects a non-admin actor"`) was deleted. The behavior it guarded moved to `requireAdmin` in `src/routes/users.ts:8-11`, but no test exercises `requireAdmin` or `handleDeleteUsers` with a non-admin actor. The authorization guard is now completely unguarded by any test in the tree.

- **{src/api/users.ts:11-18, scope: introduced, issue: partial batch failure leaves deletions applied but unaudited, evidence: grounded: read src/api/users.ts, src/util/audit.ts}** — For `ids = [a, b, c]` where `c` doesn't exist: `deleteUserRecord` is called for `a` and `b` (real state mutation via `src/store/db.ts:16-18`), then the loop throws `NotFoundError` on `c` and `recordDeletion` (line 18) is never reached. The result is that two users are actually deleted with zero audit trail of it — the one piece of new functionality this change adds (`recordDeletion`) is exactly what gets skipped on the partial-failure path. Since `recordDeletion` is new, this isn't a "regression" against prior behavior, but it is a defect in the replaced code: the batched implementation has no atomicity and no partial-audit recording, so a mid-batch failure produces real side effects with no record of what happened.

### Cleared
- Admin-role guard: re-established at `src/routes/users.ts:8-11,15` (see above).
- `DeleteUserRequest`/`handleDeleteUser` names: retired, no remaining references (grep-verified).
- Import of `ForbiddenError` moved from `src/api/users.ts` to `src/routes/users.ts:2` — straight relocation, not a loss.
